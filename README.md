# TEST TTS — آزمایشگاه محلی گفتار فارسی

رابط گرافیکی محلی برای آزمایش **MOSS-TTS v1.5 8B** با متن فارسی، صدای مرجع و مدل ماندگار در حافظه. تنظیمات اولیه برای Windows 11، RTX 4060 Ti 16GB، Ryzen 9 7900X و RAM 32GB انتخاب شده است؛ استنتاج واقعی روی این سخت‌افزار هنوز تست نشده است.

## نصب و اجرا

1. **Python 3.11 x64** و درایور NVIDIA سازگار با CUDA 12.8 نصب باشد. CUDA Toolkit جدا لازم نیست.
2. مخزن را دانلود کن و `install_windows.bat` را اجرا کن. این مرحله اینترنت می‌خواهد ولی مدل دانلود نمی‌کند.
3. فایل‌های مدل و کُدک را مطابق بخش بعد دستی دانلود کن.
4. `start_windows.bat` را اجرا کن؛ رابط در **http://127.0.0.1:7860** باز می‌شود.
5. دو مسیر محلی را وارد کن، «بارگذاری مدل» را بزن و گزارش زنده را ببین. اولین بار ممکن است چند دقیقه طول بکشد.
6. متن و صدای مرجع اختیاری را انتخاب کن و «تولید گفتار» را بزن.

پنجره Python را باز نگه دار. تولید متن جدید و بستن مرورگر مدل را از حافظه خارج نمی‌کنند. بستن Python یا زدن توقف/آزادسازی حافظه مدل را خارج می‌کند. تنظیمات مسیر و حافظه در `settings.json` ذخیره می‌شوند؛ تغییر تنظیمات تنها پس از بارگذاری مجدد اعمال می‌شود.

## دانلود دستی

- [MOSS-TTS v1.5 8B](https://huggingface.co/OpenMOSS-Team/MOSS-TTS-v1.5/tree/main)
- [MOSS-Audio-Tokenizer اصلی](https://huggingface.co/OpenMOSS-Team/MOSS-Audio-Tokenizer/tree/main)

پوشه‌های پیش‌فرض: `models/MOSS-TTS-v1.5` و `models/MOSS-Audio-Tokenizer`.
مسیر دلخواه مانند `D:\AI\models\MOSS-TTS-v1.5` نیز قابل استفاده است. پوشه‌ای را انتخاب کن که مستقیماً `config.json` در آن قرار دارد.

**کل snapshot** را نگه دار: همه shardهای `.safetensors`، index، فایل‌های JSON، Python و وابستگی‌های نسبی آنها، tokenizer و chat template. ساختار پوشه‌ها را حفظ کن؛ صرفاً دانلود وزن‌ها کافی نیست. **کُدک v2، LoRA و GGUF جایگزین این فایل‌ها نیستند.** اگر قبلاً مدل را داری همان مسیر را وارد کن؛ کپی مجدد لازم نیست.

برنامه فایل‌های اصلی و shardهای مفقود را قبل از load بررسی می‌کند؛ خرابی محتوای shard هنگام load مشخص می‌شود. اجرای مدل local-only است و دانلود خودکار خاموش است. کد Python داخل snapshot با `trust_remote_code=True` اجرا می‌شود؛ فایل‌ها را از منبع مورد اعتماد بگیر.

## حافظه و سرعت

| حالت | مدل زبان | کُدک پیش‌فرض | کاربرد |
|---|---|---|---|
| NF4 پیش‌فرض | چهار بیتی روی GPU | CPU با FP32 | نقطه شروع کم‌مصرف برای 16GB؛ کیفیت و سازگاری نیازمند تست مقصد |
| BF16 خودکار | تقسیم لایه‌ها توسط Accelerate بین GPU و CPU | CPU | مقایسه بدون کوانتایز ۴ بیتی؛ احتمال کندی انتقال و فشار RAM |
| CPU | BF16 روی CPU | CPU | عیب‌یابی؛ برای تأخیر کم مناسب نیست |

بودجه BF16 پیش‌فرض **11 GiB GPU + 12 GiB CPU** فقط برای وزن‌های مدل زبان است. این اعداد سقف کل مصرف نیستند؛ کُدک، activations، KV cache و حافظه موقت بارگذاری جدا هستند. حالت NF4 این بودجه‌ها را استفاده نمی‌کند. Disk offload فعال نیست. در صورت OOM از NF4، کُدک CPU، متن کوتاه‌تر و توکن کمتر استفاده کن و سایر برنامه‌های سنگین را ببند.

**توکنایزر متن** همیشه CPU است. **کُدک صوتی** یک شبکه جدا و سنگین است؛ اجرای آن روی CPU حافظه گرافیکی آزاد می‌کند اما encode/decode را کندتر می‌کند. در حالت NF4 می‌توان کُدک GPU را نیز آزمایش کرد؛ جا شدن و سرعت آن تضمین نشده است. محل واقعی وزن‌ها، زمان بارگذاری و دستگاه کُدک در گزارش رابط دیده می‌شود.

پردازش سنگین در subprocess جداست، پس رابط هنگام load پاسخگو می‌ماند. تنها یک عملیات همزمان مجاز است. توقف فوری subprocess را می‌بندد و حافظه را آزاد می‌کند؛ تست بعدی نیاز به load مجدد دارد. خطای بارگذاری نیز پردازش را می‌بندد تا مدل ناقص در حافظه نماند.

## مرجع و فارسی

مرجع ۱ تا ۳۰ ثانیه، ترجیحاً ۵ تا ۱۵ ثانیه، یک گوینده و بدون موسیقی باشد. WAV پیشنهاد می‌شود؛ فایل به mono WAV تبدیل می‌شود. کدهای آخرین مرجع بر اساس SHA256 کش می‌شوند و در تست‌های بعد encode مجدد نمی‌شوند. این حالت **voice cloning** است؛ متن مرجع را به متن مقصد نچسبان.

تگ پیش‌فرض `Persian (Farsi)` است. اعراب‌گذاری خودکار یا بازنویسی محتوا انجام نمی‌شود. مدل اصلی v1.5 تنظیم شده؛ LoRA فارسی اضافه نشده است. کیفیت تلفظ و حفظ هویت باید شنیداری ارزیابی شوند.

## خروجی تدریجی و سنجش دوبله همزمان

قطعه‌های جمله‌ای پس از **تولید و decode کامل هر قطعه** برای پخش تحویل می‌شوند. این **استریم توکن‌به‌توکن یا تضمین realtime نیست**. پیش‌فرض قطعه ۱۸۰ کاراکتر و سقف ۵۱۲ توکن تولیدی است. رسیدن به سقف هشدار احتمال ناقص بودن صدا می‌دهد. قطعه‌بندی ممکن است پیوستگی لحن را تغییر دهد؛ برای مقایسه می‌توان آن را خاموش کرد.

- `first_chunk_s`: زمان تا اولین waveform آماده، با encode مرجع در تست اول؛ بدون تأخیر مرورگر/پخش.
- `elapsed_s`: تولید و ذخیره، بدون load مدل.
- `RTF = elapsed_s / audio_s`: کمتر از ۱ یعنی تولید سریع‌تر از طول صدا، ولی لزوماً تأخیر اولیه کم نیست.
- `prepare_s / generate_s / decode_s`: زمان هر مرحله برای هر قطعه.
- `peak_vram_gib`: اوج حافظه allocated در PyTorch، نه کل VRAM گزارش‌شده در nvidia-smi.

تست اول را warm-up در نظر بگیر و سپس با متن، seed و مرجع یکسان مقایسه کن. وزن‌ها گرم باقی می‌مانند اما KV cache درخواست قبلی نگه داشته نمی‌شود. اگر RTF بالاتر از ۱ باشد، کاربرد عملی به پیش‌دوبله و بافر نیاز دارد.

## API محلی

فعلاً فقط loopback است و مستقیم از گوشی قابل دسترسی نیست. مستندات در **http://127.0.0.1:7860/docs** است.

| مسیر | کاربرد |
|---|---|
| `POST /api/load` | بارگذاری با مسیرها و تنظیمات حافظه |
| `POST /api/reference` | آپلود multipart با فیلد file؛ دریافت reference ID |
| `POST /api/generate` | دریافت job ID؛ متن و تنظیمات تولید |
| `GET /api/status` | وضعیت، jobها، آدرس WAV قطعه‌های آماده و نتیجه |
| `POST /api/unload` | توقف و آزادسازی حافظه |
| `GET /api/log` | انتهای گزارش worker |

نمونه بعد از بارگذاری مدل در رابط:

```python
import requests, time
base = 'http://127.0.0.1:7860'
r = requests.post(base + '/api/generate', json={'text': 'سلام! این یک آزمایش است.', 'chunked': True})
r.raise_for_status()
job_id = r.json()['id']
seen = set()
while True:
    state = requests.get(base + '/api/status').json()
    job = next(j for j in state['jobs'] if j['id'] == job_id)
    for url in job['chunks']:
        if url not in seen:
            seen.add(url)
            print('WAV ready:', base + url)
    if job['state'] != 'running':
        print(job)
        break
    time.sleep(0.5)
```

هنگام مشغول بودن، عملیات جدید 409 می‌گیرد. فایل‌ها در `outputs/<job_id>/` شامل WAV کامل، قطعه‌ها و `metrics.json` ذخیره می‌شوند. uploads/outputs خودکار پاک نمی‌شوند؛ در صورت نیاز دستی پاک کن. آخرین ۱۰ job در API وضعیت دیده می‌شود.

## پشتیبانی چندمدلی

پروفایل‌های فعلی **MOSS-TTS v1.5 8B** و **MOSS-TTS 1.0 8B** هستند؛ هر دو MossTTSDelay. نسخه 1.0 نیاز به snapshot جدا و تغییر مسیر دارد. انتخاب اسم پروفایل محتوای مسیر را تغییر نمی‌دهد؛ مسیر تعیین‌کننده وزن اجراشده است.

مرز آداپتور `tts_lab/moss.py` شامل `load(config, emit)` و `synthesize(text, reference, options, emit)` است. Chatterbox، Pocket و MOSS Realtime به آداپتور واقعی و وابستگی و تست جدا نیاز دارند؛ قرار دادن وزن آنها در پوشه پشتیبانی خودکار ایجاد نمی‌کند. در رابط نیز پشتیبانی‌نشده‌ها عرضه نشده‌اند.

تست‌های نرم‌افزاری: فایل ناقص، تقسیم فارسی، API/مرجع و lifecycle پردازش با backend ساختگی. این‌ها جای اجرای وزن واقعی را نمی‌گیرند. **استنتاج، کیفیت صوت، سازگاری bitsandbytes روی Windows و سرعت/اوج حافظه روی 4060 Ti در محیط توسعه تأیید نشده‌اند.**
